# Бюджет исследования — S2-07 (подготовка)

Работа стеком на S2-06 (#18) и актуальную S2-09 (#15). Очередь под ревью не изменена.
Отдельного PR пока нет: лимит четырёх открытых PR достигнут. Эта ветка не считается готовым
research-сценарием: его собирает S2-10.

## Реализовано

- `domain.budget.Limits`: 6 источников, 3 вызова, 20 000 входных токенов, 120 секунд,
  2 ₽ на запуск / 200 ₽ в день, RUB (ADR-0002). Общий output_tokens обязателен при создании.
- `application.budgeted_llm.BudgetedClient`: резерв до вызова. Форматное исправление
  `call_parsed` проходит ту же проверку и считается отдельным вызовом. Тариф должен быть
  известен, конечен и в валюте бюджета. Лимит одного ответа уменьшается до остатка бюджета.
- `PostgresBudgets`: отдельные короткие транзакции резервирования и завершения; сеть между
  ними. Единый порядок блокировок день → запуск сериализует конкурирующие workers. Дневная
  политика одна: попытка создать запуск с другим дневным лимитом отклоняется.
- Долговечные pending/finished call_id запрещают повтор после перезапуска. Результаты модели
  не сохраняются здесь: их сохраняет сценарий S2-10; pending не разрешает второй вызов.
- Токены и стоимость сохраняются по каждому вызову, включая ошибки. При неуспехе, неизвестной
  стоимости, таймауте или исключении резерв не освобождается, запуск остановлен. Исключение
  программирования пробрасывается. Неизвестное списание не считается нулевым.
- Перед отказом сохраняются причина и checkpoint; следующее платное действие не начинается.
  Чужой model_id/call_id — ошибка с сохранением резерва. Разные валюты не суммируются.
- `reconcile(day, provider_spent)` принимает сверенное суммарное списание поставщика в RUB.
  Оно поднимает дневной учёт, если поставщик списал больше локального отчёта; следующие вызовы
  прибавляются к скорректированной базе. Сверка во время pending-вызовов отклоняется, чтобы
  последующее освобождение резерва не уменьшило подтверждённые расходы. Автоматического
  запроса баланса провайдера нет. Старое меньшее значение не понижает дневной учёт.
- Миграция `s207_budget` после `0002`: budget_days и research_budgets. Идентификатор не занимает
  числовую ревизию под согласованную зону A evidence.version. При будущих параллельных миграциях
  потребуется согласовать ancestry в ревью. Проверен переход с очереди без потери задания.

## Как подключать

Запуск создаётся с business day и timezone-aware now в деловом поясе. При смене дня старый
запуск прекращает новые LLM-вызовы. 120 секунд проверяются перед шагом; текущий HTTP-вызов
ограничивается таймаутом адаптера. Простой входит в этот интервал — это более строгая граница,
а не обещание учета только активных миллисекунд. Перезапуск не сбрасывает этот срок.

Сборка клиента: `MaskingClient(BudgetedClient(raw_client, ...))`. Счётчик получает ровно
маскированный request, включая system, user, schema и фактический формат провайдера. Нельзя
передавать счётчик, который видит только user-текст. Поле count_input — проверенная верхняя
оценка входных токенов; ошибочная недооценка записывается фактическим usage и может остановить
следующий вызов, но не может отменить уже оплаченный запрос. Клиент возвращает обычный LlmResult;
BudgetExceeded перехватывает вызывающий сценарий и выставляет budget_exceeded.

Состояние бюджета хранится отдельно от job checkpoint; checkpoint в research_budgets не исчезает
при откате job-транзакции. Дневная строка общая для research и черновиков, если вызывающие
сценарии используют этот ledger. Runtime ещё не подключён к нему: этот шаг — S2-10 / S3-04.

## Что не закрыто и не выдаётся за проверенное

1. В старой карточке 3000 output tokens на запуск; позднее владелец утвердил 8000 на отдельный
   вызов. Общий лимит запуска не выбран автоматически: обязательный аргумент Limits.output_tokens,
   вопрос владельцу задан в чате. Значение в тестах — тестовая политика, не решение команды.
2. Реального откалиброванного счётчика для выбранного провайдера в этой ветке нет. Без count_input
   вызов отклоняется. Эвристика «символы / 3» из старой ветки не переносится. Для допуска живых
   вызовов нужны измерения провайдера на том же запросе/модели и проверка верхней оценки.
3. Сверка provider_spent выполняется по переданным проверенным данным владельца. Автоматическая
   интеграция со списаниями провайдера, production и живые платные вызовы не проверялись.
4. Зависимость #18 остаётся с Request changes. До её исправления и приёмки перенос этой ветки
   в main не предлагается. Остальные задачи зон A уже ведёт Максим — дубль реализации не начат.
