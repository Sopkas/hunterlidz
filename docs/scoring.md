# Scoring и готовность к очереди (S2-08)

Сценарии T-03, T-04, T-05 и решение тимлида по T-06 от 13.10. Версия правил: `scoring_v1` (`hunter.domain.scoring.RULES_VERSION`). Код — `src/hunter/domain/scoring.py`, тесты — `tests/test_scoring.py`.

Основа — документ 04, «Модель оценки» и «Приоритет и готовность к контакту». Модель только предлагает признаки с доказательствами (research_v1.1, S2-01). Баллы считает код: в каждом компоненте выбирается **один** уровень с причиной, уровни не суммируются. Неизвестное даёт 0 и причину, а не отрицательный вывод о компании.

## Компоненты

| Компонент | Уровень | Когда |
| --- | --- | --- |
| ICP Fit, 0–25 | 0 / 10 / 20 / 25 | Сегмент не установлен / сегмент / сегмент и тип задачи / плюс масштаб, доступный команде |
| Buying Signal, 0–30 | 30 | Самое свежее датированное событие не старше 30 дней, **или** текущую потребность подтвердил собеседник (источник — разговор) |
| | 20 | Событие 31–90 дней назад |
| | 10 | Событие старше 90 дней **или дата неизвестна** (T-03) |
| | 0 | Нет проверяемого сигнала |
| Problem Fit, 0–20 | 10 / 15 / 20 | Гипотеза / задача подтверждена / плюс подтверждённый кейс |
| Budget, 0–15 | 0 / 5 / 10 / 15 | Нет данных / косвенный признак / подтверждённые расходы в направлении / диапазон подтвердил собеседник |
| Contactability, 0–10 | 0 / 5 / 10 | Канала нет / есть канал компании или непроверенный личный / подтверждены роль и личный рабочий канал |

Пояснения:

- **Дата события.** Месяц или год хранятся первым днём периода (S2-01) — это самая ранняя возможная дата. Свежесть считается по ней, как требует документ 11.
- **Подтверждённая потребность** даёт 30 только из разговора. Вакансия или новость на сайте — событие, и решает его возраст.
- **Подтверждённый кейс** (`confirmed_case`) — утверждение реестра S2-03, которое одобрено владельцем, разрешено для внешнего использования и имеет статус `owner_reported` или `verified`. Планируемое, отозванное и неодобренное утверждение 20 не даёт (документ 04).
- **Диапазон бюджета** из источника, а не из разговора, считается подтверждёнными расходами (10): размер компании и финансирование не доказывают бюджет задачи.
- **Контактность** берётся из сохранённых контактов, а не из ответа модели. Общий канал компании определяет `is_company_wide` из S1-13.

**Противоречия** не меняют уровни, но дают `needs_review` (документ 11):
- задача или масштаб подтверждены, а сегмент нет;
- модель указала канал ЛПР, а в базе такого контакта нет.

## Приоритет

`priority_for` из контракта S1-05: 80–100 HOT, 60–79 WARM, 40–59 WATCH, 0–39 SKIP. Порог очереди 80 — это HOT; настройка `AUTO_QUEUE_MIN_SCORE` документа 12 в v1 ему равна и читается конфигурацией S2-10. Все уровни кратны 5, поэтому сумма бывает только кратной 5: на границах достижимы 35/40, 55/60, 75/80. Сами границы 39/40, 59/60, 79/80 проверены на `priority_for`.

## Готовность к очереди сообщений — `eligibility`

| Условие | Тип | Можно ли обойти |
| --- | --- | --- |
| Запрет контакта | жёсткое | нет |
| Нет подтверждённого контакта (`verified_at`) | жёсткое | нет — HOT без контакта в очередь не идёт (T-05) |
| Нет фактов (`insufficient_evidence`) | жёсткое | нет |
| Нет оффера (`recommended_product`) | жёсткое | нет |
| WATCH или SKIP | жёсткое | нет |
| WARM | мягкое | записанное исключение оператора |
| Результат требует проверки | мягкое | записанное исключение оператора |

Исключение — `OperatorException(actor_id, reason)`: кто разрешил и почему. Без причины оно не создаётся. Оно выдаётся на один результат исследования и один score: новый результат требует нового решения, старое исключение для WARM не пропустит позже результат на проверке (S2-10).

**Что передаёт вызывающий код.** `contacts` — только контакты, которым можно писать: контакты под запретом (`suppression_key`, S1-13) убраны. `suppressed` — запрет на всю компанию. `today` — деловая дата, та же, что получил `parse_research`.

**T-06, решение от 13.10.** Исключение снимает `needs_review`, но не возвращает то, что отбросила проверка research. Факт с выдуманной ссылкой на evidence в результате не появляется, а значит, не попадёт и в черновик. Чтобы использовать такой факт, оператор добавляет настоящий источник, и факт проходит ту же проверку. Тест — `test_t06_clearing_review_does_not_bring_back_a_dropped_fact`.

## Отличия от ветки `claude/H-01-H-11-hunter-v0` (`608dc6b`)

- Версия правил — `scoring_v1` вместо `1.0`, по образцу `dedup_v1`, `case_text_v2`.
- Подтверждённый кейс определяется реестром S2-03 (одобрение, статус), а не отдельным флагом.
- Общий канал компании — из `is_company_wide` S1-13; объявлений в v0 нет.
- Исключение оператора — запись с автором и причиной, а не флаг `operator_exception`.
- Будущий сигнал — ошибка: `parse_research` такие отбрасывает.
