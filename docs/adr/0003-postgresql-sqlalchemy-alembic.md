# ADR-0003. PostgreSQL, SQLAlchemy Core и Alembic

**Статус.** Пункты 1–4 — **принято**: решение PM и тимлида (карточка S1-06, ревью ветки H-01…H-11, журнал 13.10). Пункты 5–8 отвечают на вопросы тимлида к S1-06. Они **предложены** и принимаются Approve координатора зоны A в PR S1-06.

**Дата.** 2026-10-18.

Прежний ADR-0003 в ветке `claude/H-01-H-11-hunter-v0` выбирал SQLite. В `main` он не переносится, этот документ его заменяет.

## Контекст

Документ 09 требует реляционную базу с транзакциями, внешними ключами и уникальными ограничениями, «PostgreSQL-подобные возможности». Очередь jobs хранится в той же базе. Документ 08: на пилоте до 1 000 компаний и **два одновременных research worker**. У SQLite один писатель, и это потолок уже на пилоте (решение PM, карточка S1-06).

## Решение

### 1. PostgreSQL — источник истины (принято)

Всё состояние Hunter хранится в PostgreSQL. Что для этого нужно от базы и чего нет у SQLite:
- конкурентная запись двух worker;
- захват job через `SELECT … FOR UPDATE SKIP LOCKED` (T-18);
- частичные уникальные индексы, например один активный лид на company + campaign (S1-09);
- транзакционный DDL: миграция либо применяется целиком, либо откатывается.

### 2. SQLAlchemy Core, без ORM (принято)

SQL пишется явно: запросы, блокировки и проверка версий (`version`, документ 10) видны в коде. Доменные типы — неизменяемые dataclass контракта S1-05. ORM-модели дублировали бы их вторым набором классов с собственным состоянием.

### 3. Миграции — Alembic (принято)

Схема меняется только миграциями Alembic. Первая миграция, место в пакете и команда применения — S1-07.

### 4. Раскладка каталогов и HTTP API (принято)

Раскладка `domain / application / infrastructure / presentation / runtime` принята (`docs/architecture.md`, согласовано тимлидом в ревью ветки H-01…H-11). Хранилище — `infrastructure`, его интерфейсы — в `application`.

HTTP API `/v1` в v0 не делается: потребителя нет. Таблица `/v1` документа 10 остаётся контрактом сценариев (журнал, 13.10).

### 5. Синхронный доступ к базе (предложено — вопрос 1)

**Решение:** синхронный SQLAlchemy Core.

| | sync | async |
| --- | --- | --- |
| Конкурентность пилота | Два worker — два процесса, каждый со своим соединением. Конфликты решает база (`SKIP LOCKED`, версии) | Даёт параллельность внутри процесса, а её требования не просят |
| Долгие вызовы | Вызов LLM всё равно ждёт ответа с таймаутом (S2-04), worker в это время ничего другого не делает | Выигрыш, только если один процесс ведёт много исследований сразу |
| CLI (`hunter …`) | Обычные функции | `asyncio.run` в каждой команде |
| Тесты | Обычные `pytest` | Нужен плагин и event loop в фикстурах |
| Транзакции | `with engine.begin():` | То же, плюс ошибки «соединение из другого loop» |

**Последствие.** Если библиотека Telegram-панели (S3-05) окажется асинхронной, она вызывает синхронные сценарии через `asyncio.to_thread` или работает отдельным процессом. Переход на async возможен позже: сценарии и порты от него не зависят, меняется `infrastructure`.

### 6. Драйвер — psycopg 3 со встроенным libpq (предложено)

`psycopg` + `psycopg-binary`: libpq внутри колеса, на машине ничего ставить не нужно. Есть колёса для Windows, Python 3.12–3.14. Это основной драйвер PostgreSQL для SQLAlchemy 2.

Альтернатива — `pg8000`, чистый Python. Её сокеты видит сетевая защита тестов, но она тянет четыре пакета (`scramp`, `asn1crypto`, `python-dateutil`, `six`) и не основной драйвер SQLAlchemy. Защиту решает пункт 8, поэтому `pg8000` не нужен.

**Важно для S1-07.** `HUNTER_DATABASE_URL` — обычный `postgresql://…`. Для такого адреса SQLAlchemy 2.0 выбирает **psycopg2**, которого у нас нет. Движок создаётся с явным `drivername="postgresql+psycopg"`, как в `tests/test_database.py`. Формат переменной для пользователя не меняется.

### 7. CI: PostgreSQL только на Linux-джобах (предложено — вопрос 2)

Service-контейнеры GitHub Actions работают только на Linux-раннерах. Варианты для `windows-latest`:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **(а) Тесты хранилища пропускаются на Windows** — выбран | Три обязательные джобы и их имена не меняются. На Linux база обязательна (`HUNTER_TEST_DATABASE_REQUIRED=1`): пропуск там — ошибка, а не тихий зелёный CI | Хранилище на Windows в CI не проверяется |
| (б) Запускать PostgreSQL, предустановленный в образе Windows | Хранилище проверяется и на Windows | Другая мажорная версия, чем в compose и проде. Время старта. Зависимость от состава образа GitHub |
| (в) Отдельная джоба для базы | Явно | Меняет набор обязательных проверок в защите `main`. Решение владельца репозитория |

Почему (а) достаточно:
- SQL выполняется сервером, а сервер везде один — Linux-образ `postgres:18.6-alpine`.
- Платформенный риск на Windows — загрузка колеса `psycopg-binary`. Его проверяет `test_bundled_libpq_is_loaded` на каждой джобе.
- Разработчики на Windows гоняют тесты хранилища локально с базой из compose.

### 8. Тесты и сетевая защита (предложено — вопрос 3)

Проба 18.10 с защитой из `tests/conftest.py` в редакции S1-03 (Windows 11, Python 3.14, база из compose):

| Соединение | Что было | Видит ли защита |
| --- | --- | --- |
| psycopg, `localhost` | Отказ: защита запрещала DNS даже для `localhost` | да |
| psycopg, `127.0.0.1` | Соединение | **нет**: libpq открывает сокет в C, мимо модуля `socket` |
| psycopg, `10.255.255.1` | **Уходит в сеть**, ждёт таймаут 2 с | **нет** |
| pg8000, любой адрес, включая `127.0.0.1` | Отказ | да, но строже, чем нужно |

Иначе говоря, защита не пускала тесты в локальную базу по имени и при этом не замечала libpq по IP-адресу.

**Решение (сделано в этом PR):**
- DNS разрешён только для имён loopback: `localhost`, `127.0.0.1`, `::1`.
- Хост PostgreSQL проверяется на входе драйвера: `psycopg.connect` и `psycopg.Connection.connect`. Не loopback — отказ и запись в список попыток, тест падает. SQLAlchemy зовёт `psycopg.connect` через ссылку, взятую при импорте, поэтому подменяются обе точки. Тест — `test_guard_stops_libpq_before_a_remote_host`.
- Адрес тестовой базы — только из `HUNTER_TEST_DATABASE_URL`, через фикстуру `database_url`. Без переменной тест хранилища пропускается с причиной. При `HUNTER_TEST_DATABASE_REQUIRED` — падает.
- Изоляция тестов друг от друга (транзакция с откатом, DDL в PostgreSQL транзакционный) — S1-07, вместе с первыми таблицами.

## Локальная база

`compose.yaml`: `postgres:18.6-alpine`, база, пользователь и пароль `hunter`, данные в томе `hunter-db`. Порт открыт только на loopback, в обоих семействах: `127.0.0.1` и `[::1]`.

Привязка `::1` нужна. На Windows `localhost` сначала разрешается в `::1`. Без привязки соединение не отклоняется, а висит до таймаута (замер: 15 с), и только потом libpq переходит на `127.0.0.1`. С привязкой — 0,03 с.

Это база для разработки и тестов, не для прода: пароль известен, резервного копирования нет. Как разворачивать прод — документ 12, вне S1-06.

## Зависимости

Точные версии. Все выпущены не позже чем за две недели до решения и имеют колёса для Windows и Python 3.12–3.14.

| Пакет | Версия | Выпуск | Почему эта |
| --- | --- | --- | --- |
| SQLAlchemy | 2.0.54 | 15.09.2026 | Зрелая ветка 2.0. Ветка 2.1 вышла 24.09 и получила пять патчей за три недели; переход — отдельным PR |
| alembic | 1.20.0 | 11.09.2026 | Последняя |
| psycopg, psycopg-binary | 3.3.6 | 18.09.2026 | Последняя |
| Mako, MarkupSafe, typing_extensions, tzdata (Windows) | 1.4.3, 3.0.4, 4.16.0, 2026.5 | — | Транзитивные. Закреплены в `requirements.txt`, чтобы установка везде была одинаковой |
| greenlet | 3.5.6 | 14.09.2026 | Транзитивная от SQLAlchemy, ставится только на x86_64, AMD64, aarch64 и ppc64le (маркер SQLAlchemy), на macOS arm64 её нет. Закреплена с тем же маркером. Пропущена в первой редакции, найдена на ревью #10 |

Транзитивные пакеты pytest в `requirements-dev.txt` (iniconfig 2.3.0, packaging 26.3, pluggy 1.6.0, Pygments 2.21.0, colorama 0.4.6 на Windows) с S1-03 не были закреплены, и CI брал pluggy 1.7.0 трёхдневной давности. Закреплены здесь же.

Проверка, что закреплено всё: `pip install --dry-run --ignore-installed --report report.json -r requirements-dev.txt` — каждый пакет из отчёта есть в `requirements.txt` или `requirements-dev.txt` с точной версией.

Образ `postgres:18.6-alpine` — 21.09.2026, текущая мажорная версия.

## Последствия

- **S1-07:** движок с `postgresql+psycopg`; первая миграция Alembic и команда её применения; изоляция тестов.
- Тесты хранилища используют фикстуру `database_url` и не читают `HUNTER_DATABASE_URL`: рабочая база разработчика в тестах не участвует.
- Обновление SQLAlchemy до 2.1, драйвера или образа — отдельным PR с этим ADR.
