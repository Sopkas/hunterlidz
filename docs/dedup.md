# Нормализация и дедупликация компаний

Задачи S1-09 (компании, T-01 и T-02) и S1-13 (контакты, T-15). Версии правил: `dedup_v1` (`hunter.domain.dedup.NORMALIZATION_VERSION`) и `contacts_v1` (`hunter.domain.contacts.CONTACT_RULES_VERSION`).

Основа — документ 03, раздел «Дедупликация», и документ 10. Ключ компании — нормализованный регистрируемый домен по списку публичных суффиксов. Компании не объединяются по похожему названию. Домен уникален у активной компании, а неоднозначное объединение делает человек. У компании одна активная возможность в кампании.

## Канонический URL — `canonical_url`

Одна запись на страницу. Результат проходит проверку `Source.canonical_url` из S1-05.

| Что | Правило | Пример |
| --- | --- | --- |
| Схема | Только `http` и `https`. Без схемы подставляется `https`. `mailto:`, `tel:`, `ftp:`, `javascript:` → `UrlError` | `example.com` → `https://example.com/` |
| Хост | Нижний регистр; IDN → punycode; без `www.` (и `www.www.`) и без точки в конце. Повторная нормализация даёт тот же адрес | `https://www.Пример.РФ.` → `https://xn--e1afmkfd.xn--p1ai/` |
| Порт | Стандартный убирается. 0, больше 65535 или не число → `UrlError` | `:443` убран, `:8443` остаётся |
| Логин и пароль в адресе | Убираются: в базе они не нужны | `https://u:p@a.ru` → `https://a.ru/` |
| Путь | Регистр сохраняется; `/` в конце убирается; не-ASCII → `%XX`; `%7e` → `~` | `/о-нас/` и `/%d0%be-…` дают один путь |
| Query | Трекинг-параметры отбрасываются. Остальные сохраняются и сортируются по имени | `task.php?id=1` ≠ `task.php?id=2` |
| Фрагмент | Отбрасывается | `#contacts` |
| `\` в хосте | `UrlError`: браузер читает `example.com\@evil.com` как `example.com`, а `urlsplit` — как `evil.com` | |

**Трекинг-параметры:** `utm_*`, `roistat*`, `yclid`, `ysclid`, `gclid`, `gbraid`, `wbraid`, `dclid`, `fbclid`, `msclkid`, `igshid`, `mc_cid`, `mc_eid`, `_ga`, `_gl`, `_openstat`, `openstat`, `etext`.

**Остаются, хотя в старой ветке отбрасывались:** `ref`, `from`, `source`. Ошибки здесь неравноценны. Если отбросить параметр, который выбирает страницу, две разные страницы станут одним источником. Если оставить трекинг, появится лишь дубль источника.

## Ключ компании — `company_domain`

1. Канонический URL, затем хост.
2. Регистрируемый домен по списку публичных суффиксов, вместе с частными суффиксами: `name.github.io` и `shop.msk.ru` — отдельные сайты. Список берётся из пакета `publicsuffixlist` (снимок внутри пакета, без сети). Брать последние две части адреса нельзя: `alpha.co.uk` и `beta.co.uk` — разные компании.
3. **Конструкторы сайтов, которых нет в списке** (`SUBDOMAIN_HOSTS`: `tilda.ws`, `ucoz.ru`, `narod.ru`, `nethouse.ru`, `turbo.site`, `wordpress.com`, `business.site`, `wixsite.com`…). Сайт здесь — поддомен. Без этого правила все сайты на Tilda стали бы одной компанией: `company_domain("a.tilda.ws") == "a.tilda.ws"`.
4. **Общие площадки** (`SHARED_PLATFORMS`) → `None`. Страница компании там лежит по пути, а домен никому из исследуемых не принадлежит: `vk.com/alpha` и `vk.com/beta` — не одна компания. В списке:
   - соцсети и мессенджеры: `vk.com`, `t.me`, `tenchat.ru`, `max.ru`, `youtube.com`…;
   - маркетплейсы и каталоги: `ozon.ru`, `wildberries.ru`, `avito.ru`, `2gis.ru`, `pulscen.ru`, `yell.ru`…;
   - реестры и закупки: `rusprofile.ru`, `checko.ru`, `sbis.ru`, `zakupki.gov.ru`, `nalog.ru`…;
   - бесплатная почта: `gmail.com`, `mail.ru`, `bk.ru`, `inbox.ru`, `list.ru`, `yandex.ru`, `ya.ru`, `rambler.ru`, `outlook.com`… Корпоративный адрес даёт домен компании: `sales@alpha-trade.ru` → `alpha-trade.ru`. Адрес на бесплатной почте о компании ничего не говорит.
5. **Сокращатели ссылок** (`URL_SHORTENERS`: `bit.ly`, `clck.ru`, `vk.cc`, `goo.gl`, `tinyurl.com`…) → `UrlError` с кодом `shortener`. Настоящий адрес за сокращателем неизвестен, поэтому импорт просит полный адрес, а не создаёт компанию без ключа.
6. `None` также для IP-адреса, однословного хоста (`localhost`), самого публичного суффикса (`co.uk`) и неизвестного TLD (`example.notatld`). Неизвестный TLD скорее опечатка, чем новый домен. Цена `None` — компания без автоматического сопоставления, а не ложное слияние.

## Сопоставление — `match_company`

| Ситуация | Результат |
| --- | --- |
| Есть активная компания с тем же доменом | `MATCHED`, её id (T-01). Название может отличаться: ключ — домен |
| Домен совпал у объединённой записи | `MATCHED`, id компании, в которую её объединили (цепочка `merged_into_id`) |
| Домена нет или он новый | `NEW`. Активные компании с тем же нормализованным названием попадают в `similar_ids`, а `needs_review` = true (T-02). Объединяет только человек |
| Две активные компании с одним доменом | `DuplicateDomainError`: нарушено правило уникальности документа 10, это ошибка хранилища |
| Цепочка объединения оборвана или зациклена | `ValueError` |

**Что передаёт хранилище (S1-07).** `companies` — не вся таблица, а кандидаты: компании с этим доменом, все компании их цепочек `merged_into_id` до активной и активные компании с тем же `normalize_company_name()`. Для последнего S1-07 добавляет колонку нормализованного названия с индексом — отклонение от документа 10. Если цель цепочки не передана, будет `ValueError`, а не тихая новая компания.

Нормализованное название (`normalize_company_name`) нужно только для пометки. При сравнении убираются регистр, ё/е, кавычки, знаки и правовая форма (ООО, АО, ИП, LLC…). «Ромашка Сервис» и «Ромашка Плюс» не помечаются.

## Один активный лид — `active_lead`

Открытая возможность — это лид той же компании и той же кампании не в WON и не в LOST (`CLOSED_STAGES`). NURTURE остаётся активным. Закрытые лиды остаются в истории и не мешают новому. Два активных лида — ошибка хранилища.

## Контакты — `hunter.domain.contacts` (S1-13)

Документ 03: контакт дедуплицируется по нормализованному адресу конкретного канала, одинаковое имя не основание. Документ 10: `channel + normalized_address` уникальны и входят в hash одобрения. Если адрес записать двумя способами, получатся два контакта, и запрет на контакт (T-15) не сработает на втором написании.

| Канал | Правило | Пример |
| --- | --- | --- |
| `email` | Домен в нижнем регистре, IDN → punycode; локальная часть в нижнем регистре; точки и `+теги` **не** убираются — на другом сервере это может быть другой ящик. `mailto:` и «Имя <адрес>» разворачиваются | `Иван <Ivan.Petrov@Пример.РФ>` → `ivan.petrov@xn--e1afmkfd.xn--p1ai` |
| `phone` | E.164. Российские `8…` и `7…` из 11 цифр → `+7…`; 10 цифр без кода — Россия (пилот в РФ); `+89…` → `+79…` (кода страны 89 нет, это частая опечатка). Добавочный — часть адреса: `;ext=12` | `8 (495) 123-45-67, доб. 12` → `+74951234567;ext=12` |
| `telegram` | `@name` в нижнем регистре из `@Name`, `t.me/Name`, `telegram.me/…?start=`, `tg://resolve?domain=`, `t.me/s/name`, ссылки на пост. Номер телефона хранится в форме телефона | `https://t.me/Ivan_Petrov` → `@ivan_petrov` |
| `web` | `canonical_url` из S1-09 (форма обратной связи) | `www.example.com/contacts/?utm_source=x` → `https://example.com/contacts` |
| остальные | Только пробелы по краям и внутри. Формат неизвестен, любая другая правка может склеить два разных адреса | |

**Отказ с кодом** (`AddressError.code`): `empty`; `placeholder` — «нет», «-», «n/a», «см. сайт», «не указан»; `email`, `phone`, `telegram` — не адрес канала (телефон из 5 цифр, номер без кода и не российский, имя короче 4 символов); `invite` — приглашение или ссылка на сообщение Telegram (`t.me/+…`, `joinchat`, `t.me/c/…`) не адрес человека; коды `canonical_url` для `web`.

**Колонка импорта без канала — `classify_address`.** Канал угадывается по виду: `@` или `t.me` → Telegram, адрес с `@` → e-mail, цифры → телефон, домен → web, иначе `other`. Одно значение — один адрес: «a@x.ru, b@x.ru», «+7… / +7…», «@name или +7…» дают `several`; ячейку делит импорт (S1-10) или оператор. Ссылка `wa.me/…` — личный мессенджер, а не форма сайта: канал `other`, пока в `Channel` нет WhatsApp.

**Контактность по документу 04 — `is_company_wide`.** Общий канал компании (форма на сайте, общие ящики `info@`, `sales@`, `office@`, `zakaz@`…) — 5 баллов; личный рабочий канал — до 10, если роль человека подтверждена. Сам скоринг — S2-08.

Не сделано в S1-13: российские городские номера без кода города (7 цифр) отклоняются — код города не угадать; WhatsApp и VK как отдельные каналы требуют правки контракта `Channel` (S1-05); почтовые сервисы, где точки не значимы (Gmail), не схлопываются — иначе для корпоративных серверов можно склеить разных людей.

## Чего S1-09 не делает

- **Хранение и запрос.** Уникальный индекс домена у активной компании и выборка кандидатов делаются в S1-07. Сценарий импорта created / matched / rejected — S1-10.
- **Идентификатор организации.** По документу 03 подтверждённый вручную ИНН/ОГРН важнее домена при слиянии юрлиц. В таблице `companies` документа 10 такого поля нет. Это решение для S1-07 или S4.
- **Филиалы.** Связь с головной компанией пока не моделируется.
- **SPA с `#!/`.** Фрагмент отбрасывается всегда, поэтому страницы `#!/a` и `#!/b` склеятся. Сейчас это редкость, правило можно расширить.
- **Списки площадок, конструкторов и сокращателей.** Они не полны. Новая запись меняет ключ компаний, поэтому каждое изменение повышает `NORMALIZATION_VERSION` и требует пересчёта ключей.
- **Обновление списка суффиксов.** Обновление `publicsuffixlist` тоже может поменять ключи. Версия закреплена в `requirements.txt` и обновляется отдельным PR.
