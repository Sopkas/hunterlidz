# Реестр кейсов и правило «кейс только дословно»

Задача S2-03, сценарий T-07. Версия правил: `case_text_v1` (`hunter.domain.cases.RULES_VERSION`).

## Решение

Модель о наших кейсах не пишет. Кейс попадает в сообщение одним способом: версия сообщения
ссылается на запись реестра (`case_claim_ids`), и код вставляет её утверждённую формулировку
отдельным абзацем, дословно.

Проверка не пытается понять, выдаёт ли текст планируемое за готовое. Она отвечает на вопрос
проще: говорит ли текст о нашем кейсе где-то, кроме дословной цитаты из реестра. Если говорит —
Approve блокируется до правки.

Почему так. Прежняя проверка искала «готовые» глаголы и маркер «в разработке» в одном
предложении. Ревью 2 показало четыре фразы, которые её обходят. Список слов эту задачу не
решает: формулировок бесконечно много, а утверждённая — одна.

Решение принял тимлид 13.10.2026 (вариант B в карточке S2-03).

## Правило

Текст делится на абзацы по переводам строк. Для каждого абзаца:

| Что в абзаце | Результат |
| --- | --- |
| Дословная формулировка прикреплённого кейса и больше ничего | Проходит |
| Дословная формулировка кейса, который к версии не прикреплён | `case_not_attached` |
| Любое другое упоминание кейса из реестра | `case_mention` |
| Абзац сразу перед кейсом заканчивается двоеточием | `leads_into_case` |
| Абзац сразу после кейса начинается с «он», «его», «этот», «уже» и подобных | `continues_case` |

Отдельно: прикреплённая запись, которой нет среди действующих, которая отозвана или не
разрешена для внешнего использования, даёт `claim_not_usable`.

«Дословно» не зависит от типографики: регистр, ё/е, неразрывные пробелы, кавычки, длинное тире
и точка в конце не учитываются.

## Как распознаётся упоминание

У каждой записи реестра есть поле `mention`:

| Поле | Как срабатывает | Пример |
| --- | --- | --- |
| `phrases` | Фраза встретилась целиком, по границам слов | `crm для автосервисов` |
| `objects` + `topics` | В одном высказывании есть и объект, и тема; сравнение по началу слова | `помощник` + `должник` |

Высказывание — это предложение. Соседние предложения и строки склеиваются в одно высказывание,
если следующее начинается с местоимения или «уже» либо предыдущая строка не закончена точкой.
Поэтому «Делаем помощника юристам. Он уже ранжирует должников» — одно высказывание.

Маркеры обязательны для записи со статусом `planned`. При загрузке проверяется, что маркеры
распознают собственную формулировку записи: иначе они описывают другой текст.

## Что проходит и что нет

Проходит:

- «Как у вас сейчас устроена претензионная работа с должниками?»
- «Можем автоматизировать расстановку приоритетов по должникам за две недели.»
- «Вам пригодилась бы CRM для вашего автосервиса.»

Блокируется:

- «Помощник претензионщика в разработке, но уже умеет выгружать отчёты в Excel.»
- «Мы разрабатываем помощника претензионщика. Он уже сокращает время юристов вдвое.»
- «Делали CRM для автосервисов.» — готовый кейс тоже только дословно.

Следствие для оффера: «сделаем для вас помощника по претензионной работе» блокируется, потому
что называет объект и тему вместе. Оффер формулируется как действие («автоматизируем»,
«настроим»), а не как продукт.

## Чего проверка не ловит

Это страховка, а не замена Approve. Человек по-прежнему читает каждое сообщение.

- **Пересказ без маркеров.** «Наша разработка сама расставляет приоритеты по дебиторке» проходит:
  слова «разработка» нет среди объектов. Список объектов и тем утверждает владелец реестра.
- **Подводка без двоеточия.** «Мы уже сделали такое для юристов.» перед абзацем кейса проходит.
- **Подмена букв.** Латинская «o» вместо кириллической не распознаётся. Модель так не пишет, а
  оператор — доверенный человек; защищаться от этого не стали.

## Что это меняет в других задачах

- **S3-01 (контракт сообщений).** Версия сообщения хранит `case_claim_ids`; текст кейса входит в
  `body` и в `payload_hash` уже вставленным, как его увидит получатель.
- **S3-03 (черновик).** Модель возвращает текст без кейсов и ссылки на записи. Код проверяет
  текст модели без прикреплённых записей, затем вставляет формулировки отдельными абзацами и
  проверяет итог с прикреплёнными. Место вставки выбирает S3-03; абзац после кейса не должен
  начинаться с местоимения.
- **S3-04 (Approve / Edit).** После правки оператора итоговый текст проверяется той же функцией.
- **Промпт персонализации (док. 11).** Поле `Разрешённое доказательство` остаётся контекстом для
  выбора кейса, но в `body` модель его не пересказывает.

## Что не сделано в S2-03

- Хранение реестра, версии записей и загрузчик `hunter claims load` — ждут хранилища (S1-07).
  Сейчас реестр — файл `data/case_claims.json`, записи строятся функцией `claim_from_mapping`.
- Подключение проверки к Approve — S3-04.
- Маркеры кейсов в `data/case_claims.json` предложены разработчиком и ждут утверждения
  владельцем реестра.
