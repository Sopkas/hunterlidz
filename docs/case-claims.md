# Реестр кейсов и правило «о кейсе только утверждёнными словами»

Задача S2-03, сценарий T-07. Версия правил: `case_text_v2` (`hunter.domain.cases.RULES_VERSION`).

## Зачем

Hunter пишет первые сообщения лидам. Структура сообщения (документ 05, плейбук §10): контекст → наблюдение → релевантность → **подтверждённый опыт** → один следующий шаг. «Подтверждённый опыт» — это наши кейсы из документа 01: CareerMate, приложение для пар, CRM для автомобильного бизнеса, помощник претензионщика.

Риск: модель напишет о кейсе больше, чем подтверждено. Самый опасный случай — помощник претензионщика. Его полный MVP ещё в разработке, а T-07 требует блокировать черновик, где «планируемый Excel в кейсе назван готовым».

## Правило

У кейса есть одно или несколько **утверждений** — разрешённых формулировок (документ 01, `claim_id`). Версия сообщения ссылается на утверждения через `case_claim_ids`. Проверка `check_case_text` блокирует Approve, если:

| Код | Когда |
| --- | --- |
| `case_mention` | Кейс упомянут не утверждённой формулировкой: «Делали CRM для автосервисов», «Наш бот для взыскания уже работает» |
| `case_not_attached` | Формулировка процитирована, но версия сообщения на неё не ссылается |
| `claim_not_usable` | Утверждение, на которое ссылается версия, не одобрено владельцем (`approved_by`), отозвано, запрещено для внешнего использования или не существует |
| `planned_not_alone` | К формулировке планируемого кейса что-то добавлено в том же высказывании: «Вот что уже работает: …», «… , и он уже выгружает Excel» |
| `continues_case` | Следующее предложение продолжает кейс: «Он уже…», «Его используют…», «Уже сокращает…», «Которая ведёт…» |
| `not_confirmed` | В сообщении с цитатой кейса названо то, что кейс не подтверждает: Excel, ИНН, Checko, отчёты и расчёты помощника; конкурс CareerMate без первоисточника |

Готовый кейс можно вплести во фразу, как в шаблонах: «Мы разрабатывали CRM для автомобильного бизнеса, поэтому стало интересно, как у вас…». Планируемый кейс стоит отдельными предложениями, как в документе 01: «Разрабатываем помощника… находятся в разработке». Плейбук (продукт B) разрешает показывать его как проект в разработке.

«Утверждённой формулировкой» считается совпадение без учёта регистра, ё/е, неразрывных пробелов, кавычек, длинного тире и точки в конце.

## Как распознаётся упоминание

У кейса в реестре есть `mention`:

| Поле | Как срабатывает | Пример |
| --- | --- | --- |
| `phrases` | Фраза целиком, по границам слов | `crm для автосервисов` |
| `objects` + `topics` | В одном высказывании есть и объект, и тема; совпадение по началу слова | `помощник` + `должник` |

Высказывание — это предложение. Соседние предложения и строки склеиваются в одно высказывание, если следующее начинается с местоимения, «который» или «уже» либо предыдущее не закончено. Поэтому «Делаем помощника юристам. Он уже ранжирует должников» — одно высказывание.

`not_confirmed` — слова и фразы, а `*` в конце делает маркер началом слова (`отчет*`). Они проверяются только в сообщениях, где процитирован этот кейс: «отчёты у вас в Excel» в письме без кейса проходит.

При загрузке проверяется, что маркеры распознают каждую формулировку своего кейса и что формулировка сама не называет неподтверждённое.

| `claims_assistant.status` (planned) | Разрабатываем помощника для приоритизации проверки должников. Сейчас реализована оболочка Telegram-бота; обработка данных, интеграции и аналитика находятся в разработке. | Документ 01, кейс 4, допустимая формулировка |

Конкурс CareerMate не включён: документ 01 требует первоисточник до внешнего использования.

## Что проходит и что нет

Проходит:

- Шаблон документа 05 для действующего бизнеса целиком, с `auto_crm.experience`.
- Шаблон документа 05 для founder целиком, с `careermate.launch`.
- Пример плейбука §10 с `auto_crm.built`.
- «Как у вас сейчас устроена претензионная работа с должниками?» — это о лиде, не о нас.

Блокируется:

- «Помощник претензионщика в разработке, но уже умеет выгружать отчёты в Excel.»
- Формулировка помощника, а следующим абзацем «Excel-отчёты уже выгружаются.»
- «Делали CRM для автосервисов.» — готовый кейс тоже только утверждёнными словами.

## Чего проверка не ловит

Это страховка, а не замена Approve. Оператор по-прежнему читает каждое сообщение (документ 05, «Проверка перед отправкой»).

- **Пересказ без маркеров.** «Наша разработка сама расставляет приоритеты по дебиторке» и «CRM именно для автомобильного бизнеса» проходят мимо маркеров.
- **Лишний модуль у готового кейса в той же фразе.** «…CRM для автомобильного бизнеса с онлайн-записью» проходит. Запись, распределение заявок и отчётность нельзя внести в `not_confirmed`: шаблон плейбука сам спрашивает о них лида в той же фразе.
- **Подводка отдельным законченным предложением.** «Мы уже сделали такое для юристов.» перед формулировкой помощника проходит.
- **Подмена букв.** Латинская «o» вместо кириллической не распознаётся.

Следствие для писем юристам: если в письме процитирован помощник, в том же письме нельзя говорить об Excel, ИНН и отчётах, даже о клиентских. Это осознанно жёстко, потому что T-07 критический. Оператор переносит такой вопрос в следующее сообщение.

## Что это меняет в других задачах

- **S3-01 (контракт сообщений).** `message_versions.case_claim_ids` — ID утверждений вида `auto_crm.experience:v1`. У утверждения есть стабильный ключ `claim_key` и `claim_version`; в документе 10 ключа нет — отклонение для S1-07.
- **S3-03 (черновик).** В промпт персонализации (документ 11, «Разрешённое доказательство») передаются точные формулировки одобренных утверждений с указанием: использовать слово в слово, у планируемого — отдельными предложениями. Черновик проверяется с `case_claim_ids`, которые вернула модель.
- **S3-04 (Approve / Edit).** После правки оператора текст проверяется той же функцией.
- **S2-08 (scoring).** Problem Fit 20 требует подтверждённый кейс; планируемое утверждение его не даёт (документ 04).
