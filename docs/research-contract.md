# Контракт research_v1.1

Основа — `research_v1` из doc 11. Расширение `.1`: объект `offer` с полями `what_we_sell` (что продаём этому заказчику, первый этап без цены и срока) и `why` (почему — связь фактов с компетенциями и кейсом). Схема для провайдера — `application/prompts.py: research_schema()`, проверки — `domain/research.py: parse_research()`.

## Кодирование для провайдера

Структурированный вывод разных провайдеров по-разному поддерживает `null`, поэтому модель возвращает `""` для неизвестной строки или даты и `"unknown"` для неизвестного true/false. Код превращает их обратно в `None`.

## Ссылки на доказательства

Модель видит evidence под короткими псевдонимами `E1…En`; код переводит их в настоящие ID. Ссылка на несуществующий псевдоним удаляется, результат идёт на review (T-06). Для признака `relevant_case_confirmed` доказательством служит утверждение из реестра кейсов — ссылка по его ID (`auto_crm:v1`); для остальных признаков ID кейса не принимается.

## Механические проверки (doc 11)

1. JSON разбирается, лишние поля запрещены, типы и enum валидны — иначе одна попытка исправления формата.
2. `lead_id` и `company_id` совпадают с заданием.
3. Кейсы — только разрешённые активные версии реестра.
4. Положительный признак без доказательства считается неизвестным.
5. Событие с будущей датой не считается произошедшим; при точности `unknown` дата отбрасывается.
6. Лимиты длины и количества.
7. Нет ни одного прослеживаемого факта — `insufficient_evidence`, черновик не готовится.

## Статусы запуска

`completed`, `needs_review` (есть замечания проверки), `insufficient_evidence`, `budget_exceeded` (лимит doc 09, частичный результат не выдаётся за полный), `failed` (ошибка провайдера или второй неверный формат).
