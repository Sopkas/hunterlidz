# Архитектура Hunter v0

Реализация документа `09-hunter-architecture.md` и правил «Как мы работаем», часть 03. Спецификация — в базе знаний команды (`documents/`, в репозиторий не входит).

## Слои

```
src/hunter/
  domain/          сущности, правила, расчёты — без сети, БД, файлов, AI и часов
  application/     сценарии и интерфейсы адаптеров
  infrastructure/  хранилище, внешние клиенты, чтение файлов — реализуют интерфейсы application
  presentation/    интерфейс (CLI, позже Telegram) — показывает результат, не считает
  runtime/         конфигурация, связывание зависимостей, запуск
```

Зависимости идут в одну сторону: `presentation → application → domain`. `infrastructure` реализует интерфейсы `application` и использует типы `domain`. `runtime` собирает всё вместе и не содержит бизнес-правил. `presentation` получает всё через объект `App` из `runtime` и не импортирует `infrastructure` и `runtime`.

Раскладка каталогов согласована тимлидом в ревью ветки H-01…H-11 (вместо `src/api`, `src/adapters` онбординга).

Проверка направления импортов (результат должен быть пустым):

```bash
grep -rnE "^from hunter\.(infrastructure|presentation|runtime)" src/hunter/domain src/hunter/application
grep -rnE "^from hunter\.(infrastructure|runtime)" src/hunter/presentation
```

Общие доменные типы и их инварианты — контракт зон A и B: `docs/domain-contract.md`. Результат исследования и LLM-порт — `docs/research-contract.md`. Встречи, КП, заказы и оплаты — `docs/deals-contract.md`. Сообщения и согласование — `docs/messages-contract.md`.

## Принципы

- **Сценарий — единственный координатор.** Адаптеры не вызывают друг друга.
- **Время и идентификаторы — параметрами.** Домен получает `now` / `today` явно; `datetime` всегда в UTC, календарная дата — в деловом поясе (`HUNTER_BUSINESS_UTC_OFFSET`).
- **Интерфейсы — только на реальных границах**: хранилище, LLM, чтение источников, часы, личность пользователя.
- **Неизвестно ≠ ноль.** Неизвестное — `None` и причина в списке пропусков.
- **Версии — явно**: версии правил и `schema_version` в payload.

## Конфигурация

`runtime/config.py` читает окружение и `.env` (окружение важнее). Обязательна `HUNTER_DATABASE_URL` (PostgreSQL). Ошибка конфигурации — код выхода 2 до любых сетевых вызовов. Адрес базы показывается без логина и пароля.

## Хранилище

PostgreSQL, SQLAlchemy Core, Alembic, синхронный доступ (ADR-0003). `infrastructure/postgres/db.py` создаёт движок с драйвером `postgresql+psycopg` и таймаутом соединения 10 с по умолчанию и применяет миграции. `hunter migrate` — то же из CLI. Миграции — `infrastructure/postgres/migrations/versions/`, SQL в них написан явно, а значения CHECK сверяются с перечислениями домена тестом (`tests/test_storage_schema.py`).

Что гарантирует база, а не код: уникальный домен активной компании, один активный лид на компанию и кампанию, уникальный адрес контакта в канале, одна запись даты события, UUID у идентификаторов, `updated_at` (триггер), аудит только на добавление (триггер на UPDATE, DELETE, TRUNCATE). Отличия от документа 10 — `docs/domain-contract.md`.

Ограничение: аудит защищён от обычных запросов приложения и оператора. Владелец таблиц и суперпользователь PostgreSQL могут отключить триггер (`ALTER TABLE … DISABLE TRIGGER`). Владелец сейчас — тот же пользователь, под которым работает приложение: таблицы создаёт `hunter migrate` по `HUNTER_DATABASE_URL`. Значит, если приложение заставить выполнить чужой SQL, триггер не спасёт. Отдельная роль для миграций и роль приложения без прав владельца — в S4-07 или в документе 12 (ревью #14).

## Кто выполняет действие

Пользователь Hunter связан с внешней учётной записью полем `identity_id` (документ 10, таблица `users`): `os:<логин>` для локального CLI, позже `telegram:<id>` для панели. Действующий пользователь — тот, чей `identity_id` совпадает с учётной записью ОС, под которой запущен процесс (`infrastructure/os_identity.py`). Логин берётся у ОС: на Windows — `GetUserNameW` (`os.getlogin`, без учёта регистра), на Linux и macOS — по UID процесса. Переменные окружения (`HUNTER_ACTOR`, `USERNAME`, `USER`, `LOGNAME`), `.env` и аргументы команд не учитываются. `getpass.getuser()` не используется: он читает переменные окружения. Проверка — `hunter whoami` и `tests/test_access.py`, `tests/test_os_identity.py`.

Права — матрица ролей из документа 09 (`domain/roles.py`); `application/access.py` проверяет роль до действия и возвращает `FORBIDDEN`.

**Ограничение локального CLI.** Граница доверия — учётная запись ОС. Тот, кто может запускать команды под чужой учётной записью ОС или писать в базу напрямую, действует от имени её владельца. Полноценная авторизация оператора — по Telegram user ID в панели (S3-05).

## Коды выхода CLI

`0` — успех, `1` — операция отклонена (`HunterError` с кодом из документа 10), `2` — ошибка конфигурации.
